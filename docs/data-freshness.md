# 岗位新鲜度、覆盖范围与采集预算

## 本次查明的原因

2026-10-22 实际读取线上 11 个索引分片，共 19,742 条记录，最新明确发布日期是 2026-10-22，10 月发布 4,032 条。按当日 22:26 的北京时间检查，仍有 24 场后续宣讲，其中济南 15 场。仓库的 `public/jobs.json` 则停留在 2026-09-14，默认济南筛选的首条发布为 9 月 11 日。直接预览仓库静态文件，会把旧数据当成当前结果。

数据存在不等于覆盖完整：71 个配置来源中，最近 24 小时实际读取列表的只有 49 个，已知积压详情 3,212 条。部分高校轮转休眠，旧失效详情反复消耗预算；齐鲁工大公告接口还因单次正文超过 3 MB 被拒绝。不能用「快照刚生成」代替这些事实。

## 已落实的行为

- `npm run dev` 默认读取同一线上快照及其不可变分片，保留仓库旧文件作离线样本。线上请求失败会提示重试，不会悄悄替换成旧样本。手动设置 `JOB_RADAR_PREVIEW_DATA=local` 才使用本地样本，页面会明确标识。
- NAS 使用 `--freshness-first`：先给全部 17 所学校的公告、宣讲、具体岗位最新页安排有界巡检，再按剩余预算、历史进度和轮转规则补详情及历史页。公告和宣讲优先扫描最新 2 页，岗位最新 1 页；最新页阶段不用旧积压详情耗尽预算，也不挪动历史续采游标。
- 最新页阶段最多使用分片预算的 70%，单源最多 30 秒。公告每源优先处理最多 12 条最新详情、宣讲 4 条、岗位 2 条，其余继续保留在队列中。历史阶段每源最多 90 秒，NAS 采集阶段总预算由 25 分钟调为 20 分钟；下载、环境准备和构建时间另计。保留共享主机限速与 403/420/429 冷却，不以增加并发冲击上游。
- 失败详情按 2、4、8…最多 72 小时退避，新信息优先。未完成与退避项都保留；`--refresh-hours 0` 仍可显式强制复核。列表中宣讲时间、地点或岗位截止等关键字段变动会让详情缓存失效。
- 高校公告每页从 20 条缩为 10 条，公开 JSON 接口仍设 12 MB 有界响应限制；普通详情仍是 3 MB。齐鲁工大已实测读取当日 10 条公告，并通过独立工作进程完成采集、缓存复用和状态保存。
- 银行文章链接的日期解析已纠正；晚于实际观察时间的来源发布日期保留为证据，不伪造为今天发布。
- 页面展示全站最新明确发布日期、24 小时巡检覆盖、已知待补详情、当前筛选最新日期与当前城市后续宣讲。宣讲栏可展开全部场次。GitHub 每轮合并后生成新鲜度报告，超过 7 天无明确新发布、或 24 小时巡检不足半数来源时发出警告。

## 如何验证、生效

1. 本地预览刷新 `http://localhost:3000/`，确认显示「线上最新快照」和 10 月的新岗位。展开数据覆盖说明及全部宣讲日程，核对日期、学校与地点。
2. 提交并推送代码后，在 GitHub Actions 选择 **Daily Job Radar Pipeline → Run workflow**，使用普通采集选项。主工作流会同时派发 NAS 高校工作流。不要使用旧运行的 **Re-run jobs**，旧运行仍绑定旧提交。
3. 查看 NAS 的 `Collect universities on NAS` 与两条工作流的 `Audit actual data freshness and source coverage`。诊断产物中的 `freshness-report.json` 会逐源列出状态、实际列表读取时间、待补详情和失败原因。
4. 一次运行无需读完全部历史。确认新岗位和宣讲先进入页面、积压队列持续前进、超时后队列仍在，再评估是否调整预算。外部拦截、空列表或详情错误会按来源报告，不能用总运行成功掩盖。

独立只读核验命令（不采详情、不发布）：

```powershell
python scripts/audit_freshness.py --site https://sites-project.job-radar.workers.dev --output data/freshness-report.json
```

离线模式仅供调试：

```powershell
$env:JOB_RADAR_PREVIEW_DATA = 'local'
npm run dev
```
