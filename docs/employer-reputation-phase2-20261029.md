# 企业口碑第二阶段：真实来源与独立更新

本轮按使用者“继续后续功能的开发”实施，保留第一阶段企业档案、个人意向评分、v4备份和此前界面修复。代码与本地验证已完成，尚未提交、推送、部署或发布数据分支，也未触发真实Actions；不得将下面的本地试采写成线上已完成。

## 使用方式

1. 点击卡片、表格或岗位详情里的企业名称，打开“企业口碑”。匹配到收录资料时，能看到来源、原帖日期、原文入口及短摘句。
2. “员工体验”“面经”“求助讨论”分别查看；默认近一年，可以切换全部历史。工作城市、岗位、部门筛选在折叠区，未知字段默认保留。地点只取正文明确的工作地点，复用全国城市注册表，不用发帖IP、学校或企业总部推断。
3. 薪酬、工时、成长、管理的原文主题显示正向/顾虑提及数量和出处。它是规则归纳，没有把网友意见写成本站核验事实，也没有用招聘待遇承诺代替员工体验。
4. 左侧“更多条件→企业体验参考”可以选3分/4分以上；“保留评分不足的企业”默认开启。排序增加“企业体验参考优先”“我的企业意向优先”。条件可随网址、保存方案和已有浏览备份恢复，个人备注和意向评分不会进入网址或网络请求。
5. 岗位刷新会同时重读口碑索引；企业面板可独立更新/重试。加载失败保留已经加载的资料和个人草稿。口碑服务完全不可用时，页面明确提示口碑条件尚未生效，继续显示原岗位筛选结果。

## 评分规则与归属

使用可解释、版本化规则，不调用大模型给企业主观打分，也不复制平台官方星级：

- 仅近365天的员工自述体验；面经、求助、推广和传闻不参与。无日期、未来日期、未知作者账号不参与打分。
- 按原帖ID、原文链接和正文指纹去重。作者用散列账号标识，每个账号在每个维度只贡献一份均值；这是去重账号数，不是经身份认证的员工数。
- 明确正向映射5，明确顾虑映射1；同账号多次/混合观点取均值，使用5份中性3分先验平滑。每维至少10个去重账号，至少3个维度可评分才出综合参考。缺失分数为null，绝不补零或默认3分。
- 薪酬30%、工时30%、成长25%、管理15%；可评分维度按权重重新归一。疑问、传闻、否定及同句冲突倾向保守不打分。
- 综合索引最多有效24小时，也会在最早一条参与样本超出时间窗时到期；源站资料超过7天未成功读取时停止评分。导出不会延长源站读取时间。
- 只有完整名称准确对应源站企业名称才对岗位应用分数。集团品牌、简称、部门、分公司、子公司等范围仅参考，歧义匹配不自动选择。个人企业ID不变，个人意向不会混进外部分数。

面板按当前筛选重算样本；缩小城市/部门后不够门槛，会回到“评价不足”。原文主题及全部历史仍可看。评分是文字倾向参考，不是信用、事实或平台官方评分。

## 对岗位采集和页面性能的影响

**日常岗位与NAS采集工作流、预算、Python依赖、基线和导出路径均未加入口碑步骤，也不等待口碑任务。** 本轮没有重新部署NAS或修改代理。源站请求只发生在独立任务，浏览器不爬第三方企业网站。

新增 `Employer Reputation Pipeline` 每天北京时间06:30独立执行，也可手动运行。最多尝试30家，企业成功缓存48小时，失败冷却4小时，连续3次失败停批次；请求间隔至少1.5秒。采集阶段预算180秒，外层195秒终止保护，整个独立job上限8分钟（含安装、缓存与发布）。每家完成后原子保存检查点，轮转优先未尝试/较早尝试的企业；源站失败保留已有原始发表日期和摘句。

发布器只将经过校验的公开索引和内容哈希文件写入独立 `reputation-data` 分支，不改main、不部署网站，也不包含本地个人记录、源站原始HTML或诊断文件。冷缓存不会删除之前发布的企业；更新Git ref采用非强制、整树原子切换，保留上一代文件兼容正在读取的客户端。该分支不触发仅监听main的Push Checks和岗位任务。

网站先完成岗位列表，再并行读取代码随带的小种子索引和同源 `/api/reputation` 最新索引；详情打开时才加载。两条传递路径取各企业较新的成功读取，较晚抵达的旧种子不会盖掉新资料。详情需验证SHA-256及企业ID，失败可重试。API只转发固定仓库/分支下允许的文件名，5秒上游超时、短索引缓存、不可变详情缓存；前端请求8秒超时。后台数据分支更新后刷新页面/口碑即可读取，不需每次重新部署页面。

种子索引gzip数值是本地压缩估算，不是网络首屏实测。相对第一阶段，全部生产JS资产gzip合计276,885→284,244字节，增加7,359字节，包含按需面板，不是首屏传输增量。评价正文未放入 `jobs.json`、浏览分片或岗位全文索引。
