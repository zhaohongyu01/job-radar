## 3. 阶段 2：先修两个确定的数据错误

### 3.1 宣讲举办城市：补映射并统一解析

**现有入口：** `scripts/collect.py` 的 `TALK_CAMPUS_CITY`、`extract_talk_event`、`calendar_record`、`public_record`、`attach_talk_events`；`scripts/campus_talks.py`；`lib/workspace.ts:upcomingTalks`。

当前 `public_record` 会对 `source_id` 以 `-talks` 结尾的记录重建活动，再在导出时关联招聘卡。因此必须验证旧数据重新导出这条路径，不能只修新采集分支。

实施步骤：

1. 新建 `config/campus-locations.json`，把现有已验证映射迁入，新增下表。每项有稳定规则 ID、学校名/明确别名、场地匹配规则、城市、依据 URL、核验日期。由 Python 读取；不要每条活动联网查学校地址。
2. 新建纯函数 `resolve_event_city(school, venue)`，或等价独立函数；无网络副作用。返回 `city`、`method`、`rule_id` 和冲突原因，未确认时 `city=null`。
3. 优先识别线上活动；线上、直播、腾讯会议等不因主办学校被硬分到线下城市。明确混合活动可保留其线下场地，需后续 mode=hybrid 明确展示。
4. 场地内明确的唯一城市可使用；多个城市、学校映射与明确场地冲突时保持未知并记录冲突。学校规则必须同时匹配学校与场地；单独“西校区”不能跨学校复用。
5. 用规则补三个学校，保留既有多城市校区规则。“山东大学”不能一律判济南；“千佛山校区”不能被子串识别成佛山市。
6. 新增可选 `TalkEvent.city_resolution`，建议 `{method:'explicit'|'campus'|'unknown', rule_id?:string, reason?:string}`。完整证明链接留在规则注册表，不在每条列表重复长 URL；详情可根据规则 ID 展示依据。
7. 确保 `public_record` 不直接信任旧的 `talk_event.city=null`；从保留的结构化活动事实重算。先重算每条来源活动，再执行 `attach_talk_events`，清理旧派生关联后重建，避免旧城市从父招聘卡回流。
8. 保持活动 ID、学校、场地原文、起止时间、来源 URL 不变。不用举办城市改写 `job.cities`。

### 3.2 工作城市：剥离公司所在地

**现有入口：** `scripts/collect.py:extract_locations_from_text`、`filter_institution_locations`、`refine_facts`、`public_record`；`scripts/parse_positions.py`；`lib/jobs.ts:locationMatch`；`scripts/coverage_report.py:location_match`。

1. 在地点解析内部引入事实种类：`workplace`（岗位地点）、`employer_address`（单位所在地）、`branch_hint`（分支线索）、`event_venue`（活动地点）。原文、来源字段、推断方法分开保存。对外继续兼容 `cities` 和 `location_evidence`。
2. 明确优先级：岗位结构化工作地点/对应表格行 > 明示的工作地点段落 > 尚未证实的分支机构线索。公司名称括号、注册地址、单位所在地、公司简介、学校页脚、宣讲场地都不能作为确定岗位城市。
3. 移除把公司括号城市追加成 `工作地点：某市（标题/单位标注地点）` 的行为。括号信息可留为单位所在地/线索，但不进入精确工作城市。
4. 修复历史回流：`public_record` 目前会保留旧地点首行。先识别并剥离“标题/单位标注地点”等旧派生后缀，再重读原始工作地点，防止修复新采集后旧证据仍把苏州带回来。
5. 有两个真实岗位工作城市时保留两个；不能简单“只取第一个城市”或“一有显式地址就把其他所有城市删掉”。工作地点按岗位表格行建立关联。
6. 分支机构没有明示工作地点时，标为待核实/可能相关；已有明确异地工作地点时不得覆盖。银行“全省分行”不能变成每个城市均有确定岗位。
7. 保留原始 `structured`、正文与来源事实；只改派生输出。建议可选增加 `location_facts`，详细原文放详情，摘要只保留筛选必要字段。前后端和覆盖报告使用同一解释。

**真实验收例：** `024e6c6324e814578c45`，微玖（苏州）光电科技有限公司 · 前台文员接待。[原公告](https://school.gxjy.sdei.edu.cn/qdu/school/companyissueinfo/edit1/27971)的工作地为北京市大兴区。预期北京 exact，苏州非 exact；公司名称仍为完整法定名称。

审计的 108 条冲突只是候选。逐类抽样处理，不能写“这 108 条全错”或直接整批删除城市。

## 4. 阶段 3：统一城市字典，但不扩大每轮网络请求

### 4.1 数据契约

新增 `config/cities.json` 为唯一人工维护的数据源，建议结构：

~~~json
{
  "version": 1,
  "verified_on": "填写实际核对日期",
  "provenance": [{"url": "填写实际使用的官方行政区资料 URL", "edition": "实际版本"}],
  "cities": [{"code": "320200", "name": "无锡", "official_name": "无锡市", "province": "江苏", "aliases": ["无锡", "无锡市"]}]
}
~~~

上面仅说明格式，**不是可直接上线的完整城市表**。采用可核验的官方行政区资料，记录版本与许可/使用范围。第一版覆盖内地省级单元下地级行政单元及直辖市，并明确处理省直管县级单元；港澳台如未提供可靠的独立地区模型，要写清边界，不伪称所有地区完整覆盖。区县消歧采用有来源的映射，未覆盖就保持未知。

对外先保留现有中文城市名数组与 `Filters.city`，行政区代码只在注册表和内部规范化使用，避免本批迁移所有历史个人设置。

### 4.2 必须修改的使用点

1. 新增 `scripts/city_registry.py`：加载、校验唯一代码/名称、解析明确地点、构建省市映射。
2. 新增生成器 `scripts/generate_city_registry.py`，从 JSON 生成 `lib/cities.generated.ts`，提供 `--check` 检测生成文件过期；TS 生成文件不可手改。采用该方式避免 Node 原生 TS 测试与 Vite 对 JSON 导入行为不同。

### 7.3 采集预算和公平性

现有 NAS 使用最新页优先、最新页总预算 70%、单源 head pass 最多 30 秒，后续每源 90 秒、采集软预算 1200 秒；云端各分片通常为 source 180 秒、shard 1080 秒。实施时核对两份 workflow 的实际值，下载、环境、上传、构建单独计时。

## 8. 阶段 7：区分仍在招、长期招聘和有效性待核实

### 8.1 现有状态继续保留

`lib/jobs.ts` 已有 `listing_status`、`lifecycle_stage`、`timeline`、`recent_change`。新增纯函数 `assessOpportunityValidity(job, now)`（Python 对应函数使用同一测试用例），返回面向用户的 `status/reason/evidence_checked_at`，不将其当成另一个独立原始真值。

### 8.2 判定顺序与实现

1. 明确撤回、明确截止已过且无有效延期证据 → closed；截止用北京时间日期边界，保留已有日期精度规则。
2. 当前正文或官方有效申请接口明确仍开放，且对应事实核验未超过配置窗口 → confirmed_open。仅能打开页面或出现在列表里不够。
3. 官方原文明确长期/常年招聘，且没有更优先的关闭证据 → long_term；说明长期招聘也需核对当前岗位，不虚构截止日。
4. 其他 → unconfirmed；注明最后“列表检查”和“正文核验”各自时间，没有就未知。超过 90 天可加陈旧提示，但不可直接改 closed。
5. 旧数据缺乏“在招”原文证据时不倒推 confirmed_open；新增 `availability_evidence` 保存核验种类、原文、来源与实际核验时间，长文本留详情。
6. 列表仅扫两页没见到原公告不能判撤回。须有明确下架证据，或完整且适用于该记录的权威范围检查；网络错误永远不等于下架。
7. 对长期未核验记录低频复查，纳入阶段 6 的固定 probe/详情预算，不增加一次全量 URL 探测。
8. 列表提供“已核验在招/含待核实”筛选与清楚标签；默认保留待核实机会，避免因严格规则突然消失大半数据。默认最新发布排序仍按真实日期，不用最近巡检时间顶到前面。
9. 个人收藏/已投视图保留已截止和待核实记录；原文找不到时展示历史事实及来源失败说明。

**必须测试：** 无截止旧公告、长期招聘、明示关闭、延期后仍开放、公告页面存在但资格未证实、仅列表刷新、网络超时、半页扫描未找到、跨北京时间零点、投影不更新时间。

## 9. 阶段 8：多意向城市与独立宣讲城市

**涉及文件：** `lib/jobs.ts`、`lib/browsing.ts`、`lib/radar.ts`、`lib/workspace.ts`、`lib/talk-events.ts`、`app/page.tsx`、`components/filter-sidebar.tsx`、`components/action-rail.tsx`，以及实际卡片/表格/详情对城市字段的使用点。

### 9.1 先定义兼容契约

- 在 Filters 新增可选 `workCities?: string[]`；为空表示全部，有值按 OR 匹配。旧 `city='全部城市'` 迁为空数组，旧单城迁一元素数组；读旧配置时才做转换。
- 统一用 `selectedWorkCities(filters)` 与 `matchSelectedWorkCities(job, filters)` 取值。完成迁移的调用点不得继续单独读 `filters.city` 得出冲突结果；旧字段暂留给旧备份兼容，不写成第二套独立状态。
- 宣讲建立独立 `AgendaFilters`：`city`、`school`、`dateFrom/dateTo`、`mode`、`eventType`。初次以原工作城市作为默认值，之后改工作城市不改变宣讲城市。日期区间按北京时间，起止含当天。
- 工作城市与宣讲城市的跨视图关系增加明确开关 `includeRelatedTalks`。新用户默认 false，岗位列表按工作地解释；迁移旧偏好时设置 true 保留原“本城宣讲关联机会”语义，并在页面明确展示开关状态。

### 9.2 必须避免的兼容错误

1. 当前 `filterJobs` 有 `talkInCity` 逻辑，会让工作在青岛、宣讲在济南的招聘卡进入济南列表。不能偷偷删掉现有行为后只改测试期望。迁移策略按上一节执行，并在有活动关联时标“本城宣讲，工作地另核”。
2. 新开关 true 时仅未来/进行中活动能补入机会列表；历史活动仍留详情，不再永久扩充工作城市匹配。用独立活动条件，不改 `job.cities`。
3. 一个岗位同时匹配北京/上海，只显示一条；显示匹配哪些意向城市。全国/全省公告仍进 possible，地点未知仍进 unknown；活动补入记录单独标识，不能在三个地点页签重复计数。
4. `personalViewFilters` 进入收藏/已投时须清空 workCities 和其他发现页限制。返回发现页恢复之前选择；不得把个人记录“筛没了”。
5. 更新 `restoreBrowsing` 白名单、默认筛选、重置、筛选方案 `loadPresets`、导入导出和页面 query 同步（若存在）。不能只让侧栏按钮工作，而刷新/恢复方案失效。
6. 多城市偏好应保存城市标准名称列表；无效值过滤并提示，全部城市不能与具体城市并存。旧名称通过注册表迁移，未知旧值保留可见提示，不静默变成济南。
7. 日程按学校看时，允许切全部城市并显示地点未知；学校/城市条件之间矛盾时解释为空并提供重置，不能自动切城市而不告知。

**验收：** 工作选北京＋上海，宣讲选济南，三者刷新后保持；切换工作深圳不影响济南日程；跨城公告只一条；旧单城方案恢复一致；旧个人备份仍可导入；历史宣讲不再把异地工作机会永久补入当前列表。

## 10. 阶段 9：让用户判断“我能投哪个岗位”

1. 保留招聘批次 `types`（校招/社招）含义，另外新增可选 `employment_type`：full_time / internship / part_time / unknown；实习不是毕业届别，也不强行归社招。
2. 仅从明确工作性质或岗位事实提取；“实习经历优先”不等于实习岗位。新增筛选后，原校招/社招、届别和学历筛选组合仍有效。
3. 优先使用 `positions[]` 的真实岗位名、城市、专业、学历、届别、招聘人数和源表格链接。未知标待核实，不从整篇公司简介填入每个岗位。
4. 专业＋学历＋城市联合筛选必须由**同一岗位行**满足，不能拿北京研发岗的城市和上海财务岗的专业拼出一个不存在的北京财务岗。
5. 公告卡显示匹配岗位数和匹配岗位名，可展开其它岗位。保留公告原 ID 与完整表格；若将岗位拆成独立卡，需源岗位稳定 ID/明确复合键、父公告关联、去重与收藏迁移，另作为子任务验收，不以数组序号生成持久 ID。
6. 资格三态：满足明确条件 / 存在明确不符 / 信息不足待核实。不要把平台规则表述成正式录用资格；能查看原文依据。未填专业、未给薪资、未说明经验均不等于不符合。
7. 薪资保留原值、币种、单位（月/年/天）、范围和薪数；第一版只在单位明确且可比时参与筛选/排序。面议/单位不明不补 0、不根据公司名估薪；年薪转换不得再乘一次薪数。
8. 卡片主按钮按证据选择官方申请入口、原公告或第三方线索，保留来源身份。相同企业首页 URL 不能作为合并岗位/活动的唯一键；不能虚构“前往投递”直达职位。

**验收：** 同一公告两地两专业不能交叉误匹配；实习经历优先仍是全职；学历缺失出现在待核实；月薪、年薪、日薪及面议不混排为错误高薪；跨校转载和真实不同岗位不错误合并。

## 11. 阶段 10：可安排的宣讲日程

### 11.1 事件类型与事实

1. 保留 `TalkEvent` 向后兼容，新增可选 `event_type`（talk/interview/test/job_fair/guidance/other/unknown）、`mode`（offline/online/hybrid/unknown）、`registration_url`、`access_policy`、`status`（scheduled/cancelled）、`event_updated_at`。
2. 旧数据没有类型时显示“校园活动·类型待核实”，不要默认所有都是宣讲。判定优先明确结构化字段/官方标题，不因正文包含“面试”就把整场宣讲改成面试。
3. “校外能否入场”必须有学校明确规则；没有证据显示未说明。不能把公开页面误解为校外人员一定可入场。
4. 增加今天、未来 7 天、自选日期、学校、线上/线下、类型筛选；线上活动可选“包含不限城市的线上场次”，不要伪造举办城市。列表显示活动日期、开始/结束、学校、校区/地点、报名、来源。
5. 活动 ID 不含可变化的时间/场地，优先来源稳定 ID。改期或换教室保留同 ID，记录事件专用变更与实际核验时间；取消不再进入可参加列表，但已收藏日程保留取消提示。
6. 当前 `extract_talk_event` 对取消直接返回 None。需在原始状态保留旧活动事实与取消证据的 tombstone，避免取消后被静默删除、无法通知已收藏用户；不能反过来继续展示为可参加。
7. 新增独立的活动收藏数据，以 event.id 为键；取消收藏活动不取消招聘卡收藏，隐藏岗位也不能悄悄删除活动收藏。明确“发现日程”和“我的日程”的过滤规则。

### 11.2 日历文件导出

新增 `lib/calendar-export.ts` 和纯函数测试。按 [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545) 生成 UTF-8 `.ics`：CRLF 换行，长行按字节折行，文本转义；使用稳定 UID、DTSTAMP、DTSTART。明确北京时间转换为 UTC 后输出，避免依赖设备时区。结束时间缺失不编造时长；只有日期时使用 DATE，并注明时间待确认；如有 DTEND，遵循非包含结束边界。

产品要求另行验收：标题、学校/场地、官方原文链接可在日历应用查看；禁止把原文换行注入额外 ICS 属性。改期导出保持 UID；取消信息可导出供用户核对。**下载一次文件不会自动同步后续变化**，页面必须说明。至少实际导入一种常见日历应用检查中文、时区和跨日，不只做字符串包含断言。

测试包括中文长行、逗号/分号/反斜线/换行、非法日期、仅日期、仅开始时间、跨北京时间零点、重复活动、改期同 UID、取消活动。报名/投递仍由用户自行完成，不自动访问报名提交接口。

## 12. 阶段 11：投递跟进、提醒与个人数据迁移

### 12.1 先扩展本地个人记录

现有 `Personal` 只有 saved/applied/hidden/readAt，存储键 `quancheng-personal-v1`；已有备份导入导出，支持旧版本 1/2、5 MB 和 20,000 条上限。不要把已有备份能力当作待新建功能。

1. 新增可选字段 `application_stage`（planned/applied/test/interview/offer/rejected/withdrawn）、`applied_at`、`next_action_at`、`next_action_note`、`notes`、`personal_updated_at`。个人投递阶段不能写回公开招聘 `lifecycle_stage`。
2. 保留 applied 布尔兼容值：至少 applied 及其后续阶段为已发生投递；回到 planned 需显式处理是否撤销已投。旧 applied=true 映射 applied，但缺失的投递时间保持 null，不用今天补。
3. 新字段第一版继续加在原存储键的记录中，避免把 saved/applied 旧数据留在读不到的位置。写入捕获配额/隐私模式异常，保留内存编辑并明确提示未保存。
4. 扩展 `validPersonal`、页面导入导出、重复来源个人状态合并和数据备份版本（新导出 v3，继续导入 v1/v2）。新版本备份要同时包含活动收藏与 AgendaFilters，避免只备份岗位。
5. 导入先完整验证再提交，禁止一边验证一边覆盖。默认合并：布尔保留现有语义，文本/阶段冲突按可信个人更新时间比较；旧记录无时间时展示冲突预览，由用户选择，不静默吞备注。
6. 备注限制 2,000 字、下一步说明 200 字，仍按纯文本渲染；日期必须是合法 ISO。保持现有文件/记录上限，超限显示实际限制；不能截断后说导入成功。
7. 数据迁移失败不得清空旧值。写入前保留用户可下载备份，测试存储写失败、备份非法、版本未知、原始 ID 合并变化、重复来源 ID、中文/换行备注。
8. 投递队列显示下一步时间，已投页可编辑阶段、备注与提醒；标记已投只改本地，不向企业发送任何内容。

### 12.2 提醒先做不依赖后台的部分

第一版提供用户主动启用的页面内截止/笔试/面试提醒、活动改期/取消提示和日历导出，显示当前浏览器本地保存限制。时间依据来自任务/活动事实，不把“无截止”猜成月底。

浏览器关闭时可靠通知、邮件/Web Push、跨设备同步需要额外服务、身份和冲突解决；本项目尚无为此建立的业务后端。此部分单列后续里程碑，先提交服务方案、费用/配额、数据保存与删除、用户订阅/退订流程，经明确选择再实现。不要用申请浏览器通知权限的按钮冒充已实现后台提醒，也不要静默上传投递备注。

### 13.4 性能与完整性门槛

- 固定同一份约 2 万条完整快照、同一台机器，修复前后各运行 3 次离线导出与城市筛选，记录中位耗时/峰值内存/资产大小。零网络修复若耗时增加超过 20%，先定位新增全量循环，解释并优化后再交付，不靠删字段提速。
- 列表筛选不对每条记录重新创建全国正则；城市表预索引，标准化结果复用。同一记录多城市命中用 Set 去重；不要每次渲染对全国每城各扫全库。
- 保留前端分片加载上限，当前最多 4 路；完整索引加载完成前显示加载状态，不显示误导性 0 条。
- 每个新增网络源有单源预算、总分片预算、检查点和下一轮续采证据；正常 NAS 采集预算不因本批直接变长。实际全流程耗时单列，不把 3 分钟日历巡检当成 20 分钟整轮采集。
- 来源数与学校数从注册表得出；预期来源集合变更要有审查记录。禁止硬编码当前 21 校、22 渠道、78 来源或固定线上记录数作为永远正确的验收。

## 14. 提交与发布：防止“代码好了，页面还是旧数据”

1. 每批完成后给用户具体差异、测试结果与本地预览证据。更新 `AI_HANDOVER.md` 的最新段落，写明完成/未完成与真实验证环境。提交/推送按用户明确授权，不代替用户作出发布决定。
2. 检查推送的目标分支和 HEAD 与被验证的代码一致。GitHub 旧运行的 Re-run 使用旧提交，不能靠重跑旧任务验证新代码。
3. 发布数据修复必须执行当前代码的重新合并/导出。`deploy_only` 复用线上旧快照，适合纯界面发布，**不能用于证明城市补正已经生效**。
