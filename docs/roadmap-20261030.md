## 三、第一批：上线与真实数据缺口

### A0：完成已开发功能的发布验收（P0）

步骤：

1. 清点现有修改和新增文件，保留之前界面、个人记录与口碑两期实现；核对所有依赖文件已经纳入交付范围。
2. 对即将发布的最终版本执行相关定向测试、lint、TypeScript、生产构建及Actionlint，不以旧测试记录代替新版本验证。
3. 得到明确的提交推送部署指令后，提交完整实现并等待Push Checks通过；按现有页面发布方式部署，保留线上完整岗位快照。
4. 手动运行独立口碑流程，核验实际数据分支写权限、报告、API、缓存、数据新旧合并，以及失败后保留旧数据。
5. 在线实测手机和桌面：打开企业面板、查看原文、筛选、个人评分保存/备份、刷新；模拟口碑不可用时岗位仍能浏览。
6. 保存发布提交、运行ID、部署版本、截图和实际耗时。出现问题时有可执行的前一版本恢复办法，不能靠清空用户个人记录解决。

验收：真实线上页面与代码版本一致；独立任务确实更新数据，页面可读取；原岗位/宣讲快照与个人记录无损。代码已构建和真实已上线分别记录。

耗时影响：页面发布验收不要求重新采集全部岗位。口碑采集180秒预算、195秒保护、独立job上限8分钟；安装和发布时间不算进源站采集预算。

### A1：补齐看准、脉脉的接入可行性验证（P0）

步骤：

1. 每个平台选若干已知企业，覆盖完整公司名、集团品牌和分公司，核对真实企业页和评价页。
2. 看准：继续检查正常公开页面的加载过程、动态数据来源、分页、评分和评价正文；不以 `robots.txt` 返回HTML或工具读不到首页文字判定整个站不可接入。
3. 脉脉：分别核对公开内容、当前自建采集器适用的访问规则，以及可取得的授权数据渠道；搜索服务的访问例外不直接套给自建采集器。
4. 两者均验证：企业ID对应是否准确、哪些字段可取得、是否含原帖日期/城市/职位、分页是否完整、失败类型、请求数和响应时间。
5. 对每个平台交付独立结论：可自动读取的范围、需要登录/授权的范围、不可用的范围和替代方式。没有确认的接口不能写成“已有开放API”，一次失败也不能写成“永远无法接入”。
6. 对可用渠道完成小样本适配与重复运行；确认真实内容和时间未被伪造后才纳入B2。若需要平台授权，明确依赖，不无限尝试，也不阻塞其他批次。

验收：每个平台都有可复核的页面/请求证据及能力清单；可接入的企业样本实际显示原文内容，并通过重复读取。只有外链或人工导入，不能算自动接入完成。

相关文件：`lib/employers.ts`、`scripts/collect_reputation.py`、`config/reputation-sources.json`，以及后续按来源拆分的适配器。

耗时影响：验证是开发期间的独立试验；不嵌入日常岗位任务。正式接入后各来源共享评价总预算并有各自子预算。

### A2：核验当前岗位与宣讲覆盖、新鲜度（P0）

步骤：

1. 读取实际生产快照及对应Actions记录，分别统计源站发布日期、实际成功采集时间、导出时间，避免“页面更新了但只有旧岗位”。
2. 先检查济南、青岛、北京、上海、广州、深圳、杭州、南京等已有测试城市，再按实际缺口扩展；逐城记录岗位与本地宣讲的来源数、成功数、最新记录、失败/冷却和待补详情。
3. 比对源站最新列表与本站样本，追查分页、缓存、时间解析、筛选和导出是否漏掉最新记录。学校在某城不等于宣讲一定在该城，活动地点和工作地点继续独立。
4. 对曾受限或陈旧的中石大/复旦日历、邮储栏目等逐个复核当前状态，不照搬历史结论。可用的补适配，受限的明确保留缺口。
5. 针对漏采原因修复最新页巡检、详情失败重试、历史续采与轮转；不重采全部历史，不用删除旧记录换成功率。
6. 设与来源更新频率、轮转周期相符的新鲜度标准。不能把全部轮转来源都机械套成24小时必须更新。

验收：逐城逐源提供对照清单，样本中的源站新岗位/新宣讲能解释是否收录和原因；新增修复保持原ID、别名、收藏和投递身份。来源数量、城市可选数量与真实成功覆盖分别报告。

耗时影响：优先在现有云端/NAS单源与分片预算内改进请求分配和续采，不直接增加全站抓取页数；记录修复前后实际整轮时间及剩余待采数量。

## 四、第二批：把企业口碑变成可用的数据产品

### B1：以真实在招企业生成口碑优先队列（P1）

1. 从当前完整岗位快照提取去重企业，优先准确名称、有在招岗位、岗位数量多和口碑过期的企业；不读取或上传用户本机收藏、投递和备注来决定服务端队列。
2. 将人工验证的企业ID映射和动态优先队列分开；没有可靠对应的企业记录为待匹配，不靠模糊简称强行合并。
3. 增加队列状态、最近尝试、最近成功、有无实际内容、失败冷却及下次调度；持续失败的热门企业不能一直占满预算，低优先企业也应有轮转机会。
4. 给来源设置子预算，共用180秒总预算、195秒保护、缓存和检查点。页面成功却没有帖子与网络失败分别统计；“无内容”也不冒充已覆盖评价。
5. 在信息来源面板提供有内容企业数、近期体验企业数、可评分企业数和更新失败数。详细采集诊断放在维护视图，不堆到求职卡片。

验收：优先50家真实在招企业都有“已匹配/有内容/无内容/受限/待核对”的明确状态；重复运行后按新鲜度推进，而不是每次从固定名单第一家开始。并不预先承诺这50家都能取得评价或评分。

### B2：多来源模型、评价质量与评分展示（P1）

1. 将现有硬编码的 `provider: nowcoder`、来源URL校验和文件标识改为版本化的来源适配约定，支持A1确认可接入的来源；保留旧种子、缓存与客户端兼容。
2. 企业身份保留来源ID、完整名称、集团/子公司/分公司范围、已核对别名。跨平台对应必须有证据，不能更换已有个人企业记录的归属键。
3. 统一原帖日期、成功读取时间、工作城市、职位、部门、内容类型和出处。日期缺失保持未知；重新导出和缓存命中不刷新原始日期。
4. 原帖ID/链接、转载指纹和账号分别去重。跨平台无法确认是不是同一个人的，不声称已获得独立员工人数。
5. 用真实样本审核疑问、传闻、推广、否定、跨企业推荐和矛盾意见分类；做人工标注样本回归，报告误分类，不将推测自动写成企业事实。
6. 平台原生评分单独显示来源、满分尺度、样本数和读取日期；本站文字倾向参考分单独显示规则和依据，不直接平均不同尺度或把面试分算成在职体验分。
7. 保留当前每维10个去重账号、至少3个维度、近一年、源站超7天停分等保守规则；没有证据支持前不因零企业出分而降低门槛。
8. 卡片继续轻量展示，完整证据、适用城市/部门和来源差异在面板内查看；未匹配、暂无内容、读取失败、样本不足分别显示。

验收：来源、日期与原文可追溯；集团资料不误套子公司；跨来源转载不重复抬高样本；不够样本仍不出分；默认保留未评分岗位；旧个人数据和分享筛选继续有效。

耗时影响：分类和导出以已取得内容离线处理，不为每张岗位卡重复请求企业；新增处理时间单独测量，采集仍不超过独立预算。

### B3：企业聚合页（P1）

1. 以现有保守企业身份聚合准确对应的在招岗位、历史机会、宣讲活动、面经和员工体验。存在集团范围或名称歧义时明确分组，不把所有同品牌企业混在一起。
2. 支持在企业内筛选岗位工作城市，宣讲仍按举办城市独立展示；未知地点保留并说明。
3. 保留各岗位自己的投递入口、截止时间、收藏、投递阶段；公司层面的个人意向继续复用第一阶段记录。
4. 给企业页提供稳定可分享地址，刷新和浏览器前进/后退都能恢复；不能把私人备注或意向评分放进网址。
5. 所有资料基于已有索引聚合，评价和正文按需加载。先实现“看一家企业的全部机会”，不依赖账号系统。

验收：同一企业多条岗位和多场宣讲可统一浏览；当前抽屉只显示一条“当前招聘机会”的缺口得到补全；子公司与分公司边界清楚，深链不泄露个人数据。

耗时影响：前端聚合，不新增源站采集请求；性能随大样本实测。

## 五、第三批：已有求职流程与性能补全

### C1：待投递入口一致性及阶段总览（P1）

已确认的具体缺口：`TopActionCard` 的数字使用 `buildActionQueue`（已收藏、未投递、未隐藏、未截止），点击却进入 `saved` 全部收藏；`filterJobs` 的saved条件没有这些队列限制，导致数字和打开列表不同。

1. 为待投递增加明确视图，统一使用相同条件与截止排序；“我的收藏”继续保留所有收藏，不能靠删除已投递/已截止收藏来凑数量。
2. 更新浏览状态、网址枚举、备份恢复和旧版本默认值；点击待投递后，当前发现页城市、届别和评分筛选不应藏掉已收藏任务。
3. 在已有投递阶段记录上增加总览：准备投递、已投递、笔试/测评、面试、Offer、未通过、主动结束；先支持列表/分组和可访问的按钮操作，不强制依赖拖拽。
4. 沿用现有跨页锁与字段冲突逻辑，阶段总览和详情快捷操作修改同一记录，不另建一套状态。

验收：顶部待投递数与打开的条目一致；全部收藏不丢记录；阶段修改跨页面一致，草稿和投递时间保留。

相关文件：`components/top-action-card.tsx`、`lib/workspace.ts`、`lib/jobs.ts`、`lib/browsing.ts`、`lib/personal-records.ts` 和对应测试。

### C2：岗位截止与个人跟进日历（P1，本轮暂缓）

1. 在已有校园宣讲ICS导出的基础上，新增个人收藏岗位截止、个人下一步跟进事项，允许选择要导出的类型。
2. 日期型截止作为北京时间全天事项；精确时间型保留原时间。原文未知日期不制造提醒日期。
3. 用稳定UID避免重复导入重复事项；同一事项变更后可以识别更新。备注是否进入导出由用户明确选择，默认使用最少必要内容。
4. 提供周/月视图或按日清单，手机端可直接操作；与投递阶段、已截止处理保持一致。

验收：真实日历应用中导入一次及重复导入、日期型/精确型、改期/取消都实际检查。语法单测通过不等于外部日历已经验收。

耗时影响：本地导出和展示，不新增源站请求。

### C3：继续降低完整索引的解析与内存开销（P1/P2）

现有首片和按需详情已经完成，不重做。历史完整浏览列表仍约37.6MB JSON、4.8MB gzip，后续优化必须保留完整机会与筛选语义。

1. 用同一份完整快照记录冷启动首卡、全部可筛选时间、解析阻塞、内存、全文搜索和慢网失败恢复，区分首屏与全量加载。
2. 排查重复解析、重复传输与重复计算，按快照ID复用已校验数据；测量后决定是否把全文搜索/大索引处理移入Web Worker。
3. 若继续缩投影或拆分索引，保留薪资、地点证据、资格对应、变更、别名和完整搜索还原；必须说明哪些结果是预览、哪些是完整统计。
4. 保留原索引兼容与内容哈希校验，失败不显示伪全量结果，暖刷新失败保留可用旧快照。

验收：同快照的岗位ID、筛选结果、全文搜索、宣讲归属、个人记录逐项一致；桌面/手机、冷/暖缓存分别报告前后数据。先有实测再定性能改善幅度，不凭代码大小承诺加载时间。

耗时影响：不增加源站网络；可能增加离线导出/构建时间，必须量化后决定是否采用。

## 六、第四批：可选的推荐与通知

### D1：求职档案与可解释匹配（P2，本轮暂缓）

1. 本地保存学历、专业、届别、意向工作城市、岗位方向等可选条件，允许跳过和清空；不要求先建账号才能浏览。
2. 复用现有资格/城市规则，区分明确符合、明确不符、信息不足；未知字段不能直接判不符合。
3. 提供“为什么匹配”和可关闭的匹配排序，不改变“全部机会”的可见性，不把企业口碑缺失当作不匹配。
4. 将档案纳入个人备份版本与恢复测试，保持备注和投递记录仍只在本机。

验收：明确同岗位资格对应，不能拿公告中不同岗位的城市、专业和学历拼成虚假的符合条件；未填写档案时正常浏览。

耗时影响：基于现有索引本地计算，无需逐岗位调用外部模型或增加采集请求。

### D2：关闭页面后的订阅通知（P2，本轮暂缓，存在服务选择依赖）

1. 先明确通知内容：收藏截止、个人跟进、宣讲改期、保存筛选的新机会；区分公开机会订阅和含私人信息的个人提醒。
2. 可先提供公开筛选RSS/日历订阅。邮件/Web Push另做轻后端方案，列明服务、费用/配额、发送去重、失败重试及运行位置；不能把页面内提醒开关称为后台推送。
3. 邮件/推送需要明确订阅、频率、暂停与退订；只保存发送所需数据，不静默上传求职备注或全部投递历史。
4. 通知任务与采集/发布分离，按快照增量生成事件，不让发送失败卡住采集；暂停或删除订阅后停止发送。

验收：关闭网页后能实际收到一次通知；不重复、不在退订后继续发送；展示时区和事项准确；无后端授权时不假装已开通。

耗时影响：新增独立通知任务与服务成本；不增加源站采集等待。具体资源估计在选定方案后提交。

公众投稿/管理员审核、跨设备同步和付费评价接口单列远期选项，本计划不把它们偷偷作为上述功能的前置条件。

## 七、预算与覆盖的取舍

| 项目 | 岗位/NAS等待影响 | 独立工作或限制 |
| --- | --- | --- |
| 两期口碑上线 | 不加入岗位等待路径 | 真实Actions/部署验收一次；口碑job最多8分钟 |
| 看准/脉脉适配、口碑队列 | 不加入岗位等待路径 | 正式源站采集总预算180秒，各来源分配子预算 |
| 岗位/宣讲补缺 | 保持现有单源/分片上限，实测变化 | 增加来源后需轮转；不能承诺每城每校每轮全量 |
| 企业页、投递总览、个人日历、匹配 | 不新增源站请求 | 本地计算、按需资产加载与性能验收 |
| 更精简索引 | 不新增源站请求 | 可能增加离线处理，需比较导出时间 |
| 邮件/推送 | 不加入岗位等待路径 | 新增通知服务、任务与费用，另行选型 |

固定预算下，来源和企业增加后，完整轮转周期可能变长。要同时扩大范围并保持原更新频率，就需要提高独立任务频次/预算或改善每次请求有效产出，必须给出实测再调整。不能同时承诺“更多全量数据、刷新一样快、耗时一点不增加”。

## 八、逐批交付要求

每批提交可复核的交付记录：改了哪些文件、来源/页面样本、目标与实际覆盖、失败或限制、定向测试、手机/桌面检查、同数据结果一致性、实际耗时和待做项。

阶段状态分开记：计划、实现、定向验证、提交、推送、部署、线上验收。功能写好不等于已上线；链接不等于已接入；样本少不等于企业差评。只改计划文档不需要重跑程序测试。

默认不新增账号、收费服务、公众评价后台或重新部署NAS；出现确实需要的服务依赖时，先拿出具体方案。未经明确指令不执行Git推送或部署。
